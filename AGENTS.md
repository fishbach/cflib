# QWEN.md

Guidance for AI assistants working in this repository.

## Project Overview

**cflib** is a C++20 library for Web 2.0 applications, providing efficient
network communication (WebSocket/RMI), serialization (BER/ASN.1), data access
(DAO over PostgreSQL/SQLite), and cryptography (Botan). Companion client
runtimes in JavaScript (`js/`) and Python (`py/`) speak the same binary
protocol to cflib C++ servers. MIT licensed, authored by Christian Fischbach
(cf@cflib.de), version 1.0.0.

Key concepts:
- **RMI** — remote method invocation over WebSocket; services are declared
  with `RMIService` classes, clients are generated from service definitions.
- **Serialization** — headers containing `SERIALIZE_CLASS` get generated
  serializer sources at build time (see "Code generation" below).
- **DAO** — data access objects for SQL backends.

## Repository Layout

| Path | Purpose |
|---|---|
| `cflib/base` | Core types: `String`, `ByteArray`, `Container`, `DateTime`, `File`, `SharedPtr`, `Url`, `Flags`, `Regex`, concurrency. Aggregated by `cflib/base.h` (the PCH). |
| `cflib/util` | Utilities: `bin2src`, `jscombiner`, `libev` helpers, `testmain` (doctest main shared by all tests). |
| `cflib/crypt` | Botan 3.13-based crypto, `pwhash`. |
| `cflib/serialize` | BER/ASN.1 serialization; `ser` generator binary, `apiexporter`, `asn1dump`; `generate/` produces C++/JS/Python API stubs. |
| `cflib/db` | SQL backends: `psql/`, `sqlite/`, `migrationmoped`. |
| `cflib/dao` | DAO layer (PSQL implementation). |
| `cflib/net` | WebSocket communication, `WSCommManager`, `RMIServer`, `fileserver/`. |
| `examples/` | `chatserver`/`chatclient` (WebSocket RMI demo), `chatclient_py`, `pgtest`, `request`. |
| `js/` | JavaScript client runtime; `js/dao` and some `js/net` stubs are generated (gitignored). |
| `py/` | Python client runtime (asyncio + `websockets`, managed with `uv`); service/DAO classes generated by `cflib/serialize/generate/python.cpp`. |
| `bin/` | Built executables land here (`cf_app` default output dir); not tracked. |
| `cmake/` | Build system: `ProjectConfig.cmake` (global config), `DependencyConfig.cmake`, `Build.cmake` (`cf_lib`/`cf_app`/`cf_test`), `Util.cmake`, `find/` (FetchContent find modules). |
| `docker/` | Dockerfile for the build environment. |

Module dependency order (per `MODULES`):
`dao → db → net → net/fileserver → crypt → serialize → util → base`

## Building and Running

```bash
cmake -B build
cmake --build build
ctest --test-dir build
```

- Requirements: C++20 compiler, cmake >= 3.28, zlib (`zlib1g-dev`); Botan and
  doctest are pulled via FetchContent. Optional: PostgreSQL (`libpq-dev`),
  SQLite — both OFF by default.
- Useful CMake options: `-DENABLE_PSQL=ON`, `-DENABLE_SQLITE=ON`,
  `-DBUILD_TESTS=OFF`, `-DBUILD_EXAMPLES=OFF`, `-DBUILD_BENCH=OFF`,
  `-DUSE_FETCHCONTENT=OFF` (system libs), `-DONLY_GENERATORS=ON`
  (build only code generators, e.g. for cross compilation; see
  `GENERATORS_BIN_DIR`).
- A `config.cmake` is searched for by walking up the directory tree and
  included if present (local, untracked build customization).
- Built apps land in `bin/` at the repo root (stripped in Release,
  debug-split in RelWithDebInfo). Generator binaries go to
  `build/generators/`.
- Tests: doctest with CTest discovery (`doctest_discover_tests`, labels
  enabled). Test targets live in `<module>/<module>_test/` subdirs and link
  `cflib_testmain`.
- Benchmarks live in `<module>/<module>_bench/`.

## Build System Conventions

All CMake targets are created via the helpers in `cmake/Build.cmake` — never
use raw `add_library`/`add_executable` in module CMakeLists.

- `cf_lib(<name>)` — library from **all** `*.h`, `*.cpp`, `*.qrc`, `*.ui`
  globbed in the current dir (+ `DIRS`). Extra args: `PUBLIC`/`PRIVATE`
  link deps, `RESOURCES` (embedded via `bin2src`), `OTHER_FILES` (IDE
  listing), `DAO <dir>`, `REMOTE_APIS ...`, `ENABLE_EXCEPTIONS`,
  `ENABLE_SER`, `PCH <header>`.
- `cf_app(<name>)` — executable, same source discovery.
- `cf_test(<name> <lib>)` — doctest executable; pass `NO_DISCOVER` for a
  single registered test instead of per-case discovery.
- **Exceptions are OFF by default** (`-fno-exceptions`); only enabled
  per-target with `ENABLE_EXCEPTIONS`.
- PCH: `cflib_base` precompiles `cflib/base.h` (PUBLIC); all other targets
  `REUSE_FROM cflib_base`. Tests reuse it by default.
- **Source discovery is glob-based**: adding/removing a normal `.h`/`.cpp`
  file requires no CMakeLists.txt edit. (Re-run cmake configure if a new
  *directory* is added.)
- Warnings: GCC/Clang `-Wall -Wextra -Wpedantic -Wcast-align
  -Wdouble-promotion -Wformat=2 -Wnull-dereference -Wunused`; MSVC
  `/W4 /WX`. Keep new code warning-clean.

## Code Generation (build-time)

- Any header containing `SERIALIZE_CLASS` (or `CFPerm`) triggers
  `ser serialize <header.h> <name>_ser.cpp` at build time; the generated
  file is added to the target automatically. Headers containing
  `RMIService` are treated as RMI service definitions instead.
- `cf_lib`/`cf_app` with `REMOTE_APIS <type...> [FOR <target>] DEST <dir>
  [cpp]` runs `apiexporter` to generate API stubs (C++ and/or other types)
  plus a `version.md` in the destination dir.
- Python client classes are generated from the same service definitions
  (`cflib/serialize/generate/python.cpp`).
- Do not hand-edit generated output (`*_autogen/`, `js/dao`, generated
  `cpp/remote/` files).

## Code Conventions

- **Header comment block** in every source file (see any existing file):
  `Copyright (C) 2013-2026 Christian Fischbach <cf@cflib.de>` /
  `This file is part of cflib.` / `Licensed under the MIT License.`
  CMake files use the same block with `#`.
- `#pragma once` in all headers.
- Namespaces: `cflib::base`, `cflib::util`, `cflib::crypt`, ... — module
  name matches the directory. `cflib/base.h` adds
  `using namespace cflib::base;` for consumers.
- Private implementation headers go in an `impl/` subdirectory of the module.
- Tests in `<module>_test/` using doctest (`TEST_CASE`/`CHECK`/`REQUIRE`);
  benchmarks in `<module>_bench/`.
- C++ standard: C++20, extensions OFF, no C++ modules.

## Git Conventions

- **Never run `git push`** — the user pushes manually.
- Commit messages: short, imperative or lowercase past-tense single line
  (e.g. `clang fixes`, `new AI overview`).

## External Client Runtimes

- `js/`: browser/node runtime mirroring the C++ net layer; stubs for
  services are generated JS.
- `py/`: asyncio-based runtime (`cflib.net.ber` hand-written BER codec,
  `cflib.net.rmi`, `cflib.net.rsig`); only third-party dep is
  `websockets`, managed with `uv`. Reference client:
  `examples/chatclient_py/`.
